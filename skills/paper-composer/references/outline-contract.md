# 用户大纲契约

## 目标

用户大纲是**内容权威**：决定论文讲什么、按什么逻辑讲、哪些结果必须突出。它不是排版模板，也不自动等于完整论文结构；缺失部分必须显式补齐。

## 最小大纲

用户至少提供以下信息。可以用聊天、Markdown、Word 或 PDF 给出；缺失项由 Agent 追问或在映射表中标记。

```markdown
# 论文主题
- 中心论点：一句话说明本文要证明什么。
- 目标单位/期刊与栏目：
- 语言：中文 / 英文
- 读者与篇幅：
- 核心贡献：
  1. ...
  2. ...

## 章节意图
### 1. 引言
- 目的：...
- 必须出现：...
- 不要出现：...
### 2. 方法
- 目的：...
- 关键设计：...
### 3. 实验
- 数据集/场景：...
- 对比方法：...
- 关键结果：...
### 4. 讨论
- 解释：...
- 局限：...
### 5. 结论
- 结论：...

## 已有材料
- 数据：`path`
- 图表：`path`，说明图表结论
- 文献：`path` 或引用键
- 既往稿件：`path`

## 边界
- 必须说：...
- 不能说：...
- 尚未完成：...
```

## 大纲展开规则

用户只给粗略提纲时，可以补齐为可写作的章节合同，但必须：

- 保留用户原有的论证顺序和重点，不擅自增加新的核心贡献。
- 把推断出的结构标记为 `inferred`，在骨架确认时请用户逐项确认。
- 不把“相关工作”扩写成未经核验的文献综述。
- 不把“预期结果”写成“实验结果”。

每个章节至少形成以下合同：

| 字段 | 要求 |
|---|---|
| 章节目的 | 这一节要完成的论证任务 |
| 关键论点 | 可判定的陈述，避免“效果很好”这类空话 |
| 证据 ID | 对应 `evidence/manifest.json` 中的条目 |
| 图表 | 将在本节引用的图表 ID |
| 引用键 | 支撑背景或对比的文献键 |
| 字数预算 | 按模板限制分配 |
| 必须说 / 不能说 | 用户或合规要求 |
| 状态 | `ready`、`gap`、`blocked`、`inferred` |

## 映射表

`outline/outline_map.md` 使用以下结构：

```markdown
| 大纲节点 | 模板章节 | 章节目的 | 关键论点 | 证据 ID | 图表 ID | 引用键 | 字数 | 状态 |
|---|---|---|---|---|---|---|---|---|
| 引言-问题背景 | 1 Introduction | 说明问题重要性 | ... | E1, E2 | - | [@key1] | 800 | ready |
| 实验-主结果 | 4 Results | 证明方法优于基线 | ... | E3, E4 | F2, T1 | - | 1200 | ready |
| 讨论-局限 | 5 Discussion | 说明适用边界 | ... | E5 | - | [@key2] | 400 | gap |
```

## 缺口处理

出现以下情况时标记 `gap`，不得自行编造：

- 论点没有任何证据 ID。
- 图表不存在、不可读或尚未生成。
- 文献只有标题或搜索摘要，没有可核验来源。
- 用户要求的内容与模板必需章节冲突。
- 关键实验条件、样本量、统计方法缺失。

向用户汇报缺口清单，说明是补数据、补文献、改论点还是删章节，并等待决定。

## 变更

用户修改大纲后：

1. 更新 `outline/outline_map.md`。
2. 标出受影响的章节和证据绑定。
3. 只重写受影响章节；涉及结构变化时重新确认骨架。
4. 在 `manuscript.yaml` 与章节变更历史中记录原因。
